<objective>
Corrigir bug crítico descoberto durante validação manual em navegador: o dashboard admin (`/pt-BR/admin`) crasha com "Erro ao carregar Dashboard" e a mensagem `Invalid prisma.$queryRaw() invocation: Raw query failed. Code: 22P02. Message: invalid input syntax for type boolean: "{"values":["...ISO_DATE..."],"strings":["deleted_at IS NULL AND created_at >= ",""]}"`.

Causa raiz: em `getReportStats` (`src/_modules/admin/admin.query.ts:261-274`), a cláusula WHERE do `$queryRaw` para a timeline diária é montada dinamicamente assim:

```ts
const conditions = [Prisma.sql`deleted_at IS NULL`]
if (startDate) conditions.push(Prisma.sql`created_at >= ${startDate}`)
if (filterCountry) conditions.push(Prisma.sql`country = ${filterCountry}`)
const whereClause = Prisma.join(conditions, ' AND ')

return prisma.$queryRaw<{ day: Date; count: bigint }[]>`
  SELECT date_trunc('day', created_at) as day, count(*)::bigint as count
  FROM reports
  WHERE ${whereClause}
  GROUP BY day
  ORDER BY day ASC
`
```

Essa composição de `Prisma.sql` aninhado dentro de outro `$queryRaw` via `Prisma.join` **não funciona corretamente** com o driver adapter `@prisma/adapter-pg` usado neste projeto (Prisma 7 com `queryCompiler`/driver adapters) — o fragmento SQL acaba sendo serializado como um valor de parâmetro (JSON com `.values`/`.strings`) em vez de ser interpolado como texto SQL literal no WHERE, quebrando a query inteira.

Purpose: Garantir que o dashboard admin carregue de forma confiável, já que ele é a tela principal usada por ADMIN/SUPERVISOR para gerenciar denúncias.
Output: `getReportStats` reescrito para montar a query da timeline diária sem depender da composição dinâmica de `Prisma.sql`/`Prisma.join` aninhados — usando branches explícitos de template literal (só existem 2 filtros opcionais: `startDate` e `filterCountry`, logo no máximo 4 combinações) ou outra abordagem que evite reinterpolar um `Prisma.Sql` já construído dentro de outro `$queryRaw` tagged template.
</objective>
